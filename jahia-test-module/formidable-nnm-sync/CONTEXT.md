# formidable-nnm-sync – Full context for AI session restoration

Everything known about this module, written so a new session can resume without the conversation that produced it. The repository-wide context is in the root `CONTEXT.md` and `AGENTS.md`.


Added under `jahia-test-module/formidable-nnm-sync/` (registered in `jahia-test-module/pom.xml`). A third module of the "copy me" family, beside the two samples. **Built and unit-tested only: never deployed on a running Jahia** (26 tests green, `mvn -o -pl jahia-test-module/formidable-nnm-sync verify` passes, including the dependency analysis and the bundle).

## The need

Besides the standard save, a form must reach a third-party system (the "NNM" system) in two calls:

1. **At publication**, the form's configuration: an id, a version and its flat list of fields.
2. **At each submission**, the submitted values, carrying the configuration id and version.

The submission must stay fast: the call goes out **after** the visitor is answered, a failure is **never shown** to the visitor, and a **timeout** bounds it. No authentication yet (to be added later). The real URLs are not known: placeholders in the module's `.cfg`.

## Why the built-in forward action does not fit

`ForwardSubmissionFormAction` (`fmdb:forwardAction`) only sends `multipart/form-data`, once per submission, synchronously, to a target picked by id from `org.jahia.modules.formidable.formActions.target-<id>.cfg` (`id`, `label`, `url`, `development`). No JSON, no custom header or authentication, no field mapping, no way to send a payload at publication. The response body is discarded, a non-2xx fails the submission (502), no retry. Its SSRF guard and HTTP client live in the engine's non-exported packages (only `engine.api` is exported, `formidable-engine/pom.xml`), so another bundle cannot reuse them. The engine is left **untouched on purpose** (compatibility with future versions); the integration is a separate module that depends on `engine.api` only.

## The API contract (given by the user)

Configuration payload (POST, JSON): `{ "id": <form system name>, "version": <int>, "fields": [ { "key", "type": "text"|"email"|"multiselect", "isMandatory": bool, "options": [ { "code" } ] (choice fields only) } ] }`. Flat: no steps, no fieldsets, no labels.

Submission payload: `{ "submissionId": <uuid generated by Jahia, unique per submission>, "configId", "configVersion", "timestamp": "2026-10-21T14:32:05Z", "locale": "fr", "sourceUrl", "fields": [ { "key", "value": string | [string] } ] }`. A multiselect value is an array.

Response: `201` accepted · `400` validation errors (`errors[]` per field) · `404` unknown form/configuration · `409` already received (same `submissionId`) · `413` payload too large · `5xx` technical. The user's example had typos (a missing comma, a `;` for `:`); they confirmed those are typos.

## Design (what the module does)

| Class | Role |
|---|---|
| `fmdbnnm:syncAction` (`definitions.cnd`) | The action an author adds to a form's action list. Its presence connects the form (nothing is sent for a form without it). `> jnt:content, fmdbmix:formAction, fmdbmix:readOnlyCompatibleAction, mix:title`: it writes nothing to the repository on submission |
| `PublicationListener` | `DefaultEventListener`, live workspace, `/sites`, `setAvailableDuringPublish(true)`, reacts to `j:lastPublished` added/changed, climbs to the nearest `fmdbmix:formRoot`, calls `ConfigSynchronizer.syncLater`. Pattern copied from jExperience's `MappingRuleSyncListener`, without its removal handling |
| `ConfigSynchronizer` | Debounce 2 s per form (a publication arrives as several event bursts), reads the live form, hashes the definition, posts only if the hash changed, as `version + 1`. `pending` set retried every 60 s with the **same number**: 5xx/IOException → pending, 4xx → logged and dropped (same body would be refused again). `force` resends the current version (used on 404) |
| `FormDefinition` / `FormDefinitionReader` | Walks `fields` → steps/fieldsets → fields by **mixin** (`SUBMITTABLE_FIELD`, never `FILE_FIELD`). `required` → `isMandatory`; `email` for `EMAIL_FIELD`; `multiselect` for `CARDINALITY_FROM_CHOICES` (checkbox) with >1 option; else `text`. JSON written **by hand** (org.json's key order is undefined, the hash must be stable) |
| `SyncState` (`InLive`) | Version + hash per form, in the **live workspace only**, `/nnmSync/<form uuid>` (`nt:unstructured`). Not on the form node: a publication copies default-workspace properties over live ones and would undo a counter. Written only after a 2xx |
| `SubmissionFormAction` | `FormAction` for `fmdbnnm:syncAction`. Builds the body (a few JCR reads, no network), hands it to the dispatcher, **never throws**. If the form has no stored version it sends nothing and asks for a forced sync |
| `SubmissionDispatcher` | Pool of 2 daemon threads, bounded queue of 200 (full → drop with a warning). 201/409 ok · 404 → forced resync of the configuration (that submission is lost) · anything else logged. No retry of a submission, the visitor is never told |
| `SubmissionPayload` | Only the fields the configuration declares go out (a captcha token or technical field never does); empty values are left out; `timestamp` truncated to seconds, UTC |
| `NnmClient` | `configurationPid=org.jahia.test.modules.formidable.nnmsync`: `configUrl`, `submissionUrl`, `connectTimeoutSeconds` (3), `requestTimeoutSeconds` (10). One `java.net.http.HttpClient`. **The one place to add authentication** (`post`) |

Defaults shipped in `META-INF/configurations/org.jahia.test.modules.formidable.nnmsync.cfg`: `http://localhost:9090/api/form-configs` and `.../api/form-submissions` (placeholders).

Choices that deviate from the first plan: no SSRF guard (the URLs are operator configuration, never content, so a contributor cannot redirect a submission); nothing is sent when a form is unpublished or loses its action (the API has no such call); no labels or per-language definition (the payload has none).

## Known limits

- **Options from a source** (`optionsMode` ≠ `manual`: category, content, configured list) are not sent: `FormidableOptionsSourceService` is not in the exported API. A warning is logged. Only hand-authored options (property `options`, each entry stored as `{"value","label","selected"}`) go out.
- A source-fed checkbox is assumed to be a group (`multiselect`).
- Number, date, color, range, hidden… fields are all sent as `text`.
- The form `id` is the node name: unique only within its parent, so two sites with the same form name collide on the third party's side.
- `locale` comes from the submission session's locale; `sourceUrl` from `Referer`, else `Origin`.
- `400` validation errors from the API are ignored by design (silent).
- **Unverified on a live Jahia**: the write to `/nnmSync` in the live workspace, event delivery to the listener, the default `.cfg` being picked up. No Cypress spec yet.

## Reusable facts learned about the codebase

- **Form tree**: `fmdb:form` has a mandatory `fields` child (`fmdb:fieldList`: steps `fmdbmix:formStep` → fieldsets `fmdbmix:formContainer` → fields) and an `actions` child (`fmdb:actionList`, `FmdbNodeName.ACTIONS`). Test mixins from `FmdbMixin`, not concrete type names.
- **Field identity**: `FmdbProperty.FIELD_KEY` (`fieldKey`) is a stable server-assigned key (survives rename/label change); the node name is the HTML `name` and the submitted key; `getIdentifier()` (the JCR uuid) changes on import or copy.
- **No form version exists** in the model, and no reusable server-side form-definition serialiser: `FormFieldMetadataCollector` (engine, package-private) is shaped for submission validation, without labels or tree.
- **Public API** (`engine.api`) is the only exported package. Names go through `FmdbMixin`/`FmdbProperty`/`FmdbNodeName`/`FmdbNodeType`, used qualified. `ChoiceOptionsResolver` only counts choices.
- **`FormActionException`**: its message never reaches the client (opaque code); only a 400–599 status is honoured.
- **Publication hooks in this repo** are JCR event listeners, not `PublicationService`: `MappingRuleSyncListener` + `MappingRuleSynchronizer` (jExperience) is the model for debounce, `pending` and retry; `FormPublicationAclSyncListener` (engine) fires on `NODE_ADDED` only (first publication).
- **JSON**: `org.json` is provided by Jahia/the engine. The jExperience module deliberately uses none.
- **Tests with mocks**: `JCRNodeWrapper.getNodes()` returns a `JCRNodeIteratorWrapper` and `getValues()` a `JCRValueWrapper[]`; create a mock **before** the `when(...)` that returns it (nested mock creation in the argument gives `UnfinishedStubbing`). `mockito-extensions/org.mockito.plugins.MockMaker` = `mock-maker-subclass` is needed, as in the other Java modules.
- **Module wiring**: the `jahia-test-module` parent has no signature requirement (unlike `formidable-jexperience-engine`, which carries `jahia-module-signature`); `Jahia-Depends` must list `formidable-engine,formidable-elements`; `_metatypeannotations=*` is needed for `@ObjectClassDefinition`.
- **Build offline works**: `mvn -o -pl jahia-test-module/formidable-nnm-sync verify`.
